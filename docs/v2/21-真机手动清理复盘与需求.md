# 真机手动清理复盘与需求

2026-09-26｜在本机由人工逐项确认、Claude 执行的一轮完整清理。目的：用真实清理过程验证分档模型，并提炼工具尚未覆盖的需求。本文不是某个开发阶段的验收记录。

## 结果

数据卷 460G：可用 25G（94%）→ 137G（69%），净增 112G。其中飞书缓存约 14G 由用户在飞书内自行清理，其余为本轮操作。

| 档位 | 内容 | 表观大小 | 实际释放 | 方式 |
|---|---|---|---|---|
| A 包管理器缓存 | npm / pip / bun / pnpm / Homebrew / Poetry | 18.8G | 10.9G | 官方命令 |
| A | uv `cache prune` | 9.8G | 1.3G | 官方命令（需先停占用进程） |
| A | Gradle caches + wrapper、Xcode DerivedData、Playwright、camoufox | 7.6G | 约 7.6G | 移入废纸篓，用户清空 |
| B 闲置项目产物 | 24 个 ≥90 天未动项目的 112 个产物目录 | 11.6G | 约 11.6G | 移入废纸篓，用户清空 |
| C 应用数据 | Chrome CacheStorage 19G + 本地模型 4G、Cursor 备份 3.7G + agent 缓存 0.87G、Claude vm_bundles 11G、IDEA 缓存 1.7G | 40.3G | 约 40G | 先退出应用，移入废纸篓 |
| D Docker | 8 个失败容器、6 个镜像、1 个卷、全部构建缓存 | 10.9G | 11.0G | docker 命令，Docker.raw 20.7G→9.7G 自动收缩 |

未动：Maven 1.4G（用户保留）、PyCharm 缓存 5.5G（运行中，用户暂缓）、iOS 模拟器 3.8G、uv 剩余缓存 12G、Docker 中的 mysql8 数据卷与 metabase、Cursor 主库 `state.vscdb`（含聊天记录）、Codex 会话。

## 发现与需求

### 1. 表观大小不等于可释放空间

uv prune 删除 9.8G 文件，磁盘只多出 1.3G：缓存与各项目 `.venv` 共享硬链接。

- 预估释放必须按 inode 去重、考虑 `st_nlink > 1`，而非直接用 du 表观值。
- 执行后以卷可用空间差值报告实际释放，与预估并列展示。

### 2. 占用者常常是隐藏的、长期驻留的

- uv 缓存锁被 claude-mem 拉起的 chroma-mcp 持有 4 天，`uv cache prune` 等锁 300 秒超时。
- 停掉 worker 后，它被当前会话的 hook 立即重新拉起；只有把「停止 → 等待 uv 进程退出 → prune」放进同一次执行才成功，之后再恢复服务。
- Docker 中 `dpage/pgadmin4` 被 pgAdmin4 Desktop 扩展容器使用，该容器不出现在 `docker ps -a` 中，只能从 rmi 的冲突报错得知。
- AI 工具隐藏目录、`~/.nvm` 下的 venv/node_modules 有进程在跑；这类隐藏工具目录不能按「项目产物」处理。

需求：占用检查要给出具体进程与来源；需要「暂停占用者 → 清理 → 恢复」的原子编排，且恢复后核验服务健康；工具安装目录（隐藏目录、`.app` 内部、IDE 扩展）默认排除出项目产物。

### 3. 应用运行态决定能否清理

Chrome、PyCharm、飞书、Cursor 的数据都要在应用退出后处理。本轮做法：先正常退出，10 秒超时后仅在用户明确要求时强制结束（Chrome）；IDE 可能有未保存改动，不代为退出（PyCharm）。

需求：条目显示「需先退出 X」及当前是否运行；提供正常退出入口，强制结束必须单独确认；优先引导应用内清理入口（IDE Invalidate Caches、飞书清理缓存）。

### 4. 移入废纸篓不释放空间

移入废纸篓在同一卷内，释放量为 0，用户清空后才生效；工具因 TCC 无权读取 `~/.Trash`，无法核对废纸篓内容，也无法区分用户自行清理（本轮飞书 14G 起初无法解释）。

需求：结果页分开显示「已释放」与「在废纸篓待清空」；清空后可一键复测；无法归因的空间变化如实标注为外部变化，不计入工具成果。

### 5. 以项目为单位呈现

74 个项目共 43.9G 产物。按最后活跃（git 最后提交与源码 mtime 取较新）分档：≥90 天 29 个 14.3G、30–90 天 9 个 4.0G、<30 天 34 个 23.5G。

- 执行前排除：隐藏工具目录 5 个、应用包内部 1 个、无 lockfile 1 个。
- 「未提交改动」与删除产物无关，但应作为提示展示。
- `build` / `dist` / `coverage` 只在同级存在工程标记文件时才视为产物，避免误伤用户资料目录。
- 产物删除后给出重建命令（`uv sync`、`npm i`、`pnpm i`）。

### 6. 大块优先，影响排序

本机最大的可处理项依次是：项目产物 44G、uv 22G、Docker 20.7G、Chrome CacheStorage 19G、Claude vm_bundles 11G。已开发的 Claude 插件、Cursor 工作区、Codex 会话只读盘点所对应的空间均在数 G 以内。

需求：首屏按实际可释放量展示前几项；阶段排期参考空间收益，优先覆盖项目产物、浏览器 CacheStorage、Docker。

### 7. 部分内容会自动长回来

Chrome 本地模型（4G）、Claude vm_bundles（11G）、各类构建缓存会在使用时重新下载。

需求：条目标注「会自动重新下载」；能关闭来源的给出方法（如 `chrome://flags`）；后续加入按周增长趋势，识别反复长回的来源。

### 8. Docker 需要专门适配

- 查看内容必须启动 daemon；工具启动的服务结束后应恢复原状（本轮检查后退出了 Docker）。
- 启动时带重启策略的容器会自行运行（某业务数据库容器）。
- compose 容器的 Image 字段不带 tag，按 `repo:tag` 匹配会把在用镜像误判为无人使用。
- 容器与卷分开判断：启动失败（退出码 1）且匿名卷为 0B 的容器可删；有数据的卷（mysql8 238MB）只展示。
- 本版本 Docker Desktop 删除后 Docker.raw 自动收缩，无需额外压缩；仍应以文件实际占用复测。

### 9. 执行过程的共同约定

以下做法在本轮被用户接受，可作为交互基线：

- 先只读报告，再逐档确认。
- 无官方命令的目录一律移入废纸篓，不直接删除。
- 每步前后测量可用空间。
- 条件性条目（Maven、Gradle wrapper、uv clean vs prune）单独确认。
- 工具改变过的环境（停掉的服务、启动的应用）在结束时恢复。

## 未覆盖

项目内散落的 AI 过程文件（临时脚本、截图、日志、草稿）本轮未处理；判断依据应为 git 的 ignored / untracked 状态加年龄，且 `.env`、本地数据库需单独保护。重复大文件未检查。
