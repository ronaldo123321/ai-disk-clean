# 子项目 1：引擎重构真机只读验收

2026-09-26｜对应计划 `docs/plans/2026-09-26-engine-rebuild-plan.md` Task 16｜本轮只运行 `dclean scan` 与不带 `--apply` 的 `dclean clean`，未执行任何清理、还原或清空。

## 实现

新引擎位于 `Sources/CleanerCore/Engine/`，与旧引擎并存，`dclean` 命令行已切换到新引擎：

- 规则包：29 条内置规则，逐条校验；通配、大小写变体、根目录、隐私区、工具数据目录均被拒绝。
- 四种识别器：规则、项目产物、Docker（仅本机 unix 套接字，不替用户启动）、空间分布（只展示）。
- 空间估算：硬链接按 inode 去重，只有全部链接都在范围内才计入可释放。
- 恢复区：`~/.dclean-v3/recovery`，同卷 rename；记录严格校验；目录用流式 SHA256 内容摘要，移动前算不出摘要的目录不移入。
- 执行器：执行前逐项复核（符号链接祖先、禁区、年龄）；审计写不进去就停止；只为会执行的项退出应用，IDE 与编辑器从不代为退出；只有登记服务确为占用者时才暂停，并以暂停前的进程号判断恢复。

每个任务都经过计划符合性与代码质量两轮审查，审查发现的问题均已修复或记入计划「不在本子项目内」。

## 与预期不符之处

1. **项目产物被拆成大量碎片（已修复）。** 首次扫描「建议」档列出 64 个项目，多数是 Python 子包里几 KB 的 `__pycache__`：没有 git 的项目以产物所在目录为项目根。修复后缓存类产物归到最近的工程标记目录（不会归到家目录的直接子目录），依赖与构建产物保持原判定；低于 1 MiB 的可执行项不展示（读不到子目录的项除外）。修复后项目项为 18 个。
2. **git worktree 无法读取提交时间。** 某项目下的 git worktree（754 MB）的 `.git` 是文件，读不到 reflog，按文件修改时间估计并保守地放在需要确认档。
3. **空间分布把项目文件夹列为「未识别」。** 本机几个存放源码的目录（合计约 37 GB），显示为「未识别」容易误导。
4. **规则覆盖缺口。** 以下目录未被规则覆盖，作为子项目 4 的素材：
   - `~/.npm` 3.4 GB：npm 规则只覆盖 `_cacache`，其余主要是 `_npx`，本机有常驻进程从 `_npx` 启动，不能直接清。
   - `~/Library/Application Support/VBLobsterAI` 3.0 GB（龙虾）、`~/.lingma` 1.6 GB（通义灵码）、`~/.cache/codex-runtimes` 1.6 GB、`~/.cc-switch` 2.0 GB。
   - `~/Library/Application Support/Cursor` 除已覆盖的缓存外仍有 6.3 GB（主要是含聊天记录的 `state.vscdb`，不应清理）。

## 过程记录

Task 15 的一名审查代理违反指示运行了一次 `dclean recovery purge --days abc`。当时新恢复区 `~/.dclean-v3` 不存在，命令无事可做；旧版 `~/.dclean-v2/recovery` 的 3 份记录经核对未受影响。此事暴露了 purge 不校验参数、无预览即永久删除的问题，已改为默认只预览、`--apply` 才删除，并严格校验 `--days`。
